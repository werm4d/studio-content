Premortem Report — May 2026 8 failure modes identified · All mitigated in recommended stack design
Gate Protocol: Run the G2 premortem before finalizing any major build, strategy, or deliverable. Prompt in /prompts/premortem_gate_G2_v1_May2026.md. Trigger: architecture committed, build ~70% complete.
F1 — Stack Overload HIGH / HIGH
RISK
Too many layers accumulated faster than any one person can master them. None reach production-ready status. Tools exist in planning documents but never produce a client deliverable.
MITIGATION
Hard cap on active stack layers. No tool enters the active stack without a runbook and a validated client deliverable. Everything else is explicitly queued with a named activation threshold.
F2 — David as Single Point of Failure HIGH / HIGH
RISK
David is the only person who knows the full stack. Two weeks of unavailability effectively pauses all CBai operations. No runbooks, no documentation, no recovery path.
MITIGATION
GitHub cbai-stack repo is the source of truth — M550 is rebuildable from the repo. Runbooks in /runbooks cover every production workflow. Travis validated each runbook independently.
F3 — ALDDB Never Populated HIGH / HIGH
RISK
The moat that cannot be replicated never gets filled because data capture is manual, inconsistent, and low-priority under deadline pressure. Every uncaptured project is a permanent loss.
MITIGATION
Structured capture form in /alddb. Four defined triggers: G0 ROM · G1 Feasibility · Permit Issued · G4 Closeout. Leo is primary entry owner — removed from David's plate.
F4 — Repo Degrades Without Governance MED-HIGH / MEDIUM
RISK
Multiple versions of the same script. Outdated standards nobody updates. A prompt library nobody uses because nobody knows which ones work. Standards drift from practice within 60 days.
MITIGATION
David owns the repo. One commit per logical change with a description. Quarterly review cadence (David + Travis, 30 min). Version dates in filenames. Outdated files archived, never deleted.
F5 — Enscape / Twinmotion Workflow Never Resolves MEDIUM / MEDIUM
RISK
Two overlapping rendering tools on the same project. Travis uses whichever he opened first. Material libraries diverge. Output looks inconsistent. Enscape subscription renews before anyone evaluates ROI.
MITIGATION
Explicit split defined: Enscape + Veras for design-phase rapid iteration. Twinmotion for final deliverable renders. One tool per project phase. Decided at kickoff. Documented in /standards.
F6 — Grant Funding With No Build Plan MEDIUM / HIGH
RISK
$25,000 arrives. Nobody is a developer. Claude Code can assist but is not a developer who shows up daily. The grant period ends with a partial prototype. The Enterprise relationship is damaged.
MITIGATION
Grant deliverable scoped honestly: a functional web prototype, not a polished SaaS platform. Claude Code build plan pre-written with explicit scope. Deliverable stated in grant narrative before submission.
F7 — A-900 Series Never Ships HIGH / MEDIUM
RISK
All four principals must contribute. There is no explicit owner. Nobody drives it to completion. It waits for a less busy time. The less busy time never comes. The brand-building opportunity is missed.
MITIGATION
Named owners per sheet. David owns A-901/902. Trevor reviews A-905. Leo writes A-907. Travis formats all sheets. Deadline: before Claymont permit resubmission.
F8 — Legal Structure Lags Operations MED-HIGH / HIGH
RISK
M4Di Inc. not formed. ALDDB ownership undocumented. Aubyn/M4D related-party transactions not formalized. Merge4Ward operating agreement incomplete. AIA C401 agreements not confirmed on active projects.
MITIGATION
Attorney this month — not next quarter. Five specific items: M4Di Inc. formation · ALDDB ownership protocol · Aubyn/M4D related-party docs · Merge4Ward operating agreement · C401 execution on Claymont + WHA Lobdell.
Result: All 8 failure modes are structurally mitigated in the recommended stack. The stack was built from the failures, not before them.
Standard Operating Procedure Preferred workflow for maintaining efficiency across the M4D / Aubyn ecosystem
Purpose: The stack only works if the habits form. The habits only form if the SOP is clear. This document defines the daily, per-project, and periodic habits that keep the CBai stack functioning as designed.
Daily Workflow
1
Start of Session — Git Pull
Travis + David · Every session · 30 seconds
Required
  • Travis: cd C:\Users\TravisDavis\Documents\cbai-stack && git pull
  • David on M550: cd ~/cbai-stack && git pull origin main
  • Ensures both machines have the latest standards, prompts, and scripts before any work begins
  • If pull fails: check internet connection, check GitHub token expiry (rotate every 90 days)
2
Claude Session Start — Load Context
David primary · Every Claude session · 2 minutes
Required
  • For new sessions: paste the project STATUS.md or session handoff document to restore context
  • Reference /standards/M4D_Production_Standard before producing any deliverable
  • Check /prompts for the relevant template before drafting from scratch
  • Confirm project PSA number, lead firm, and AOR before starting any document
3
Commit New Work to Repo
David + Travis · End of every productive session
Required
  • Any new script, prompt, standard, or runbook produced in a session gets committed before closing
  • git add . && git commit -m "one-line description" && git push origin main
  • Commit message format: verb + what changed — e.g. "Add Regrid parcel lookup script v1"
  • One logical change per commit. Do not batch unrelated changes together.
Per-Project Workflow
4
Project Kickoff — Define Tools and Standards
David · Every new project · Before first deliverable
Required
  • Confirm jurisdiction first: City of Wilmington (Chapter 48) or NCC UDC — never assume
  • Assign PSA number: M2_YYYY_### format. Confirm lead firm and AOR.
  • AIA C401 executed before permit submission on all DE projects — non-negotiable
  • Define rendering tool: Enscape/Veras (design phase) or Twinmotion (final delivery) — one tool, decided now
  • Confirm whether A-900 assembly series is required: CLT, SIP, modular, prefab, or hybrid systems
  • Create ALDDB G0 entry in /alddb/entries/ as soon as ROM is complete
5
Predevelopment — OI Tool ROM
David · G0 gate · Before any design work begins
Required
  • Run OI Tool ROM using CSI-structured unit price library and BLS OEWS regional labor data
  • State confidence level explicitly: ±30% at G0, ±15% at G1
  • Document ROM in plain language — not just numbers, but what the numbers mean for the client
  • Enter G0 data into ALDDB immediately — Leo entry owner, David provides OI Tool data
  • Run zoning analysis using /prompts/zoning_analysis prompt — confirm jurisdiction first
  • Flag Zone AE flood conditions: BFE + 1.5 ft freeboard = minimum FFE. Survey elevation required before G1.
6
Code Analysis — Trevor Review Gate
David drafts · Trevor approves · Before permit submission
Gate
  • Run code analysis using /prompts/code_analysis prompt
  • Mark all CBai outputs: PENDING TREVOR REVIEW in document header
  • Send to trevor4d@merge4design.com with project name, PSA number, specific questions, areas of uncertainty
  • Trevor returns: APPROVED / APPROVED WITH MODIFICATIONS / HOLD
  • No code analysis goes to AHJ or client without Trevor's written approval — no exceptions
  • Document Trevor's approval status in the ALDDB project entry
7
Production Handoff to Travis
David → Travis · At design development stage
Standard
  • Produce handoff file per M4D Production Standard in /standards
  • Include: PSA number, project type, AOR confirmation, rendering tool decision, A-900 requirement
  • Travis git pulls before starting — confirms he has the current production standard
  • Travis confirms receipt and reviews handoff against standard before beginning production
  • Flag any deviations from standard before production begins — not after the set is built
8
G2 Premortem Gate
David · Before finalizing any major build or strategy · 30 minutes
Gate
  • Trigger: architecture committed, build ~70% complete
  • Use prompt from /prompts/premortem_gate_G2_v1_May2026.md
  • Document failure modes and mitigations in /docs/premortem_[project]_[MMYYYY].md
  • Update the build based on structural change recommendations before proceeding
  • Go / No-Go / Proceed with Modifications — decision documented before continuing
9
ALDDB Entry at Every Gate
Leo primary · G0 / G1 / Permit / G4 · Non-negotiable
Gate
  • Triggers: G0 ROM complete · G1 Feasibility complete · Permit issued · G4 Closeout
  • Leo enters data using template in /alddb/ALDDB_capture_protocol
  • David provides OI Tool data · Travis provides Revit SF data · Trevor provides construction type
  • Save entries: ALDDB_[PSA]_[gate]_[MMYYYY].md in /alddb/entries/
  • Every project that closes without a G4 entry is a permanent loss to the ALDDB moat.
Periodic Maintenance
10
Quarterly Repo Review
David + Travis · Every 3 months · 30 minutes
Periodic
  • Review /standards — current? Update version dates. Superseded files go to /standards/archive/
  • Review /prompts — which have been validated on real projects? Mark them with a "Validated on" tag.
  • Review /scripts — any superseded? Archive with date suffix. Never delete.
  • Review /runbooks — any procedures that changed? Update before they drift.
  • Commit: git commit -m "Quarterly review MMYYYY — [summary]"
11
GitHub Token Rotation
David + Travis · Every 90 days · 10 minutes
Periodic
  • Set calendar reminder at token creation for 80-day warning — do not wait for expiry
  • Generate new token: github.com → Settings → Developer settings → Personal access tokens → Tokens (classic)
  • Update M550 remote: git remote set-url origin https://[NEW-TOKEN]@github.com/werm4d/cbai-stack.git
  • Revoke old token immediately after new one is confirmed working
  • Never commit tokens to files in the repo — environment variables or credential manager only
12
Stack Layer Promotion Review
David · When a queued item reaches its threshold
Periodic
  • A queued item moves to active only when its production threshold is met on a real client deliverable
  • L4 Bonsai-MCP activates when: Lobdell Ave site model produced, IFC exports cleanly into Revit 2026
  • Revit 2027 activates when: Claymont permit cycle complete, both machines upgraded simultaneously
  • Regrid activates when: script built, tested on Lobdell parcel, runbook written
  • Run G2 premortem gate before any layer promotion — no exceptions
  • Update this dashboard and /docs/architecture_decisions when a layer promotes
